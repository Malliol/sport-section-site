# Стек и архитектура

Решения для шага 1 из `PLAN.md` раздел 8. Проект один (не тиражируемый продукт),
мультиарендность не закладываем. Схема данных: [`db/schema.sql`](../db/schema.sql).

## 1. Главное решение

Статический сайт из YAML не подходит для ЛК, свободных мест, листа ожидания и
платежей. Берём **модульный монолит с единой БД**: один бэкенд, один источник
правды, публичный сайт рендерится из него. Два отдельных мира (статика плюс
отдельный ЛК) дают рассинхрон статуса набора и расписания.

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык и фреймворк | TypeScript, Next.js (App Router) | SSR и ISR для SEO, один язык на фронте и бэке |
| API и логика | NestJS (или route handlers Next.js для маленькой команды) | Модули, DI, границы доменов |
| БД | PostgreSQL | Транзакции для мест, JSONB для гибких полей |
| ORM и миграции | Prisma или Drizzle | Типы из схемы |
| Права | RBAC плюс привязки (CASL) | Роль даёт права, привязка ограничивает область |
| Авторизация | Телефон (SMS или Telegram-код), почта | «Аккаунт = человек» |
| Фон | BullMQ и Redis | Уведомления, рассылки, лист ожидания, напоминания о справках |
| Файлы | S3-совместимое хранилище в РФ | Сканы справок, подписанные ссылки |
| Контент-админка | Payload CMS или Directus поверх той же БД | Новости, страницы, галерея без разработчика |
| Поиск | Postgres FTS, позже Meilisearch | Хватит на старте |
| Карты | Яндекс.Карты | Для РФ точнее |
| Платежи | ЮKassa или Т-Банк, чеки по 54-ФЗ | Онлайн-оплата только в ЛК |
| Уведомления | Telegram-бот, SMS, email, PWA push | Родители в Telegram |
| Хостинг | Российский облачный провайдер, Docker, CI/CD | 152-ФЗ |

## 3. Архитектура

```
Публичный сайт (Next.js SSR/ISR)  ──┐
Личный кабинет (Next.js, PWA)     ──┼──> API (NestJS) ──> PostgreSQL
Админка контента (Payload)        ──┘        │
                                             ├─> Redis + воркеры
                                             ├─> S3 (документы, фото)
                                             └─> Платежи, SMS/Telegram, CRM, Метрика
```

Модули домена: каталог, расписание, набор, люди, финансы, документы и допуски,
события и достижения, коммуникации, контент, сведения об ОО (флаг `licensed`).
Режим лицензии и опции из `site.yml` живут в таблице `org_settings`.

## 4. Трудные места

- **Места и лист ожидания.** Триггер блокирует строку группы и проверяет число
  занятых мест, иначе два родителя займут последнее место. При освобождении
  воркер приглашает следующего и держит бронь N часов.
- **Права.** Один слой политик (CASL), проверка на уровне запросов. Для медблока
  Row-Level Security в Postgres. Журнал доступа к чувствительным данным.
- **Персональные данные детей (152-ФЗ).** Серверы и БД в РФ, согласия с версиями
  и датами, политика хранения. Медданные отдельно и зашифрованы, тренеру только
  допуск без диагноза. Зарубежным сервисам (аналитика, Sentry, почта) ПДн не слать.
- **Согласие на публикацию имени и фото.** Проверка на сервере при выдаче через
  представление `student_publishable`, не в шаблоне. По умолчанию обезличено.
- **Возраст на контрольную дату.** Группа хранит годы рождения от и до
  относительно `seasons.age_cutoff`. Функцию подбора покрыть тестами.
- **SEO и динамика.** Страницы направлений и групп на ISR с инвалидацией по
  событию. Свободные места подтягиваются клиентом отдельным запросом.
- **Совмещение ролей.** `account -> role_assignments(role, scope, scope_id)`.
  Тренер и родитель в одном аккаунте это две записи с разной областью.

## 5. Порядок работ

1. Каркас и ядро данных: схема, аккаунты, роли, области (самое рискованное).
2. Каталог и расписание, публичный сайт с подбором группы и формой заявки.
3. ЛК родителя и администратора: дети, документы, зачисление, лист ожидания.
4. Финансы: тарифы, оплата, чеки.
5. ЛК тренера: журнал, прогресс.
6. Остальные роли, режим лицензии, раздел «Сведения».

## 6. Упрощённые варианты

- **MVP без ЛК:** сайт, CRM (Bitrix24 или amoCRM), расписание в админке. Дёшево,
  но ЛК потом строить заново.
- **Готовая платформа** («Мой Класс», YCLIENTS, Спортлайзер) для кабинета, свой
  сайт как витрина через API. Быстрее, но зависимость от чужих ограничений.

## 7. Что схема БД не покрывает

Политики RLS (пишутся в миграции приложения), права по ролям (в коде), генерация
`sessions` из `schedule_slots`, перевод из листа ожидания в зачисление (фоновая
задача). Не моделировались: отбор с раундами, рассрочки, рассылки по сегментам,
электронная подпись, интеграция с 1С.
